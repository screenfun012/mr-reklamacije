# Čet — pomen (@) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** typing `@` in the composer opens a menu that narrows as you type, choosing somebody writes a mention that survives a rename, the mentioned person hears a bell, and `@svi` reaches everyone who can see that conversation.

**Architecture:** the mention is stored in the message body as `@[ime](id)` — the ID is the truth, the label is only a fallback — so the screen draws the name from the database. The people a mention may name come from a NEW endpoint inside the chat module, because no existing endpoint may be called by an account that only has chat (verified: `users`, `employees`, `roles`, `audit`, presence all demand a permission outside `INTERNAL_APP_PERMISSIONS`). The bell reuses the notifications module through `NotificationsPort`, as every other module does.

**Tech Stack:** Hono + Drizzle + Postgres · TanStack Start/Query/Router · Zod · Paraglide · Vitest.

**Spec:** `docs/superpowers/specs/2026-08-23-cet-razgovori-design.md` (§3.2 bell, §5 row 7 mention storage, §7) · **visual law:** `design_handoff_chat/cet-prototip.dc.html` · handoff `design_handoff_chat/2026-08-21-cet-KOMPLETNA-specifikacija.md` §4, §5, §7 · acceptance list `docs/superpowers/plans/2026-08-23-cet-prijemna-lista.md`.

## Global Constraints

- **No new permission.** The chat gate is `INTERNAL_APP_PERMISSIONS` (Nikola, N4). The people endpoint lives behind that same gate and nothing else.
- **A conversation the actor cannot see answers 404, never 403** — the whole module already works this way (`ChatService.requireVisible`).
- **The admin trap:** the `admin` role holds `ALL_PERMISSIONS` from the resolver and may own **zero** `role_permissions` rows. Any query that resolves "who holds permission X" must OR in `roles.code = 'admin'`. The precedent to copy verbatim is `notifications.repository.ts` → `findRecipientsWithPermission`.
- **The prototype's mention REGEX does not survive our model.** It matches a capitalised name in plain text (`L274`); we store an ID. Take its chip LOOK (`L280`) and nothing else.
- **Serbian is primary**, every string through Paraglide, `sr` + `en` both. A **new** key needs `pnpm --filter @mr/i18n run build` (not just `compile`) or typecheck stays red.
- **The server never writes Serbian.** `@svi` travels as an id with an empty name; the screen names it. (Same rule the statistics buckets follow.)
- Full gate green before every commit. Every load-bearing line proven by mutation — break it, watch the test go red, put it back.

- [ ] **Step 3: Write the parser**

```ts
/** The address `@svi` writes. Never a real user id, so the two can never be confused. */
export const MENTION_EVERYONE_ID = 'all'

export interface MentionMatch {
  start: number
  end: number
  /** What was written. Only a fallback — the name on screen comes from the database. */
  label: string
  /** A user id, or `MENTION_EVERYONE_ID`. */
  id: string
}

const MENTION_PATTERN = /@\[([^\]\n]{1,80})\]\(([0-9a-fA-F-]{36}|all)\)/g
const UUID_PATTERN = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i

/**
 * Every mention written in a message, in writing order.
 *
 * ⚠ The prototype matches a capitalised name in running text (`cet-prototip.dc.html:274`). That
 * model cannot survive a rename, so the spec chose to store the id (§5 row 7) and this parser reads
 * that instead. An id that is neither a uuid nor `all` is NOT a mention: a body is user input, and
 * a chip that points nowhere is worse than plain text.
 */
export function findMentions(text: string): MentionMatch[] {
  const found: MentionMatch[] = []
  for (const match of text.matchAll(MENTION_PATTERN)) {
    const label = match[1]
    const id = match[2]
    if (label === undefined || id === undefined) {
      continue
    }
    if (id !== MENTION_EVERYONE_ID && !UUID_PATTERN.test(id)) {
      continue
    }
    found.push({
      start: match.index,
      end: match.index + match[0].length,
      label,
      id: id === MENTION_EVERYONE_ID ? MENTION_EVERYONE_ID : id.toLowerCase(),
    })
  }
  return found
}
```

- [ ] **Step 5: The fan-out**

`NotificationsService.notifyChatMention` writes one row per recipient with `type: 'chat_mention'`, `entityType: 'chat_message'`, `entityId: messageId`, and `data: { authorName, conversationId, conversationTitle, excerpt }`. It runs through the existing `fanOut()` wrapper so a failure never fails the send.

In `ChatService.send`, after the message is stored and only when `stored.created` is true:

```ts
// Best-effort, like every other fan-out: a bell is not worth failing a message over.
const recipientIds = await this.resolveMentionRecipients(conversation, stored.message, actor.id)
if (recipientIds.length > 0) {
  await this.notifications.notifyChatMention(actor.id, { ... })
}
```

`resolveMentionRecipients` = `findMentions(body)` → if any id is `MENTION_EVERYONE_ID`, take everyone from `listPeopleFor`; otherwise take the named ids **intersected with** `listPeopleFor` (D8); always drop the actor; always de-duplicate.

In `ChatService.editMessage`, do the same but subtract everyone who already has a `chat_mention` row for this `entityId` (D7). No new table — the notifications rows are the record.
